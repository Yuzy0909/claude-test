## static-site-review スキル

ビルドツールを持たない静的HTML/CSS/JSサイトに対して、実装と同時並行でコードレビューを行い、指摘した問題をその場で修正するためのスキル。汎用的な code-reviewer エージェントとは異なり、**修正まで一気通貫で行う**ことが目的。

### 前提

- 対象は単一 `index.html`（インラインscript/style）や、npm/webpack等のビルドステップを持たないサイト
- レビューは実装の「後」ではなく「途中」で行い、指摘 → 即修正 → 次の観点、のループを回す

### レビュー観点と具体的チェック項目

#### 1. 🔒 セキュリティ

- **XSS対策**
  - `<head>` 直後に CSP（Content-Security-Policy）meta タグがあるか確認。なければ追加する
    ```html
    <meta http-equiv="Content-Security-Policy" content="default-src 'self'; img-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; script-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'; frame-ancestors 'none';">
    ```
  - インラインscript/styleを使う場合は `'unsafe-inline'` が必要になる点を明記した上で許容する（外部リソースは最小限のオリジンのみ許可）
  - `innerHTML` への未エスケープの動的値挿入がないか確認する
- **入力値のバリデーション**
  - `JSON.parse` や `dataset` 経由で読み込む属性値は、try/catch＋形状チェックを必ず行う
  - パス文字列を `src` 等に渡す箇所は、同一オリジン・相対パスのみ許可する allowlist 関数を用意する（例: `isSafeImagePath`）
  - 不正入力時は例外を投げてページ全体を壊さず、空配列やno-opで安全に握りつぶす

#### 2. ⚡ パフォーマンス

- **画像の遅延読み込み**
  - ファーストビュー外の `<img>` に `loading="lazy"` があるか確認する
  - `decoding="async"` を併用してメインスレッドのブロッキングを避ける
- **バンドルサイズ**
  - 画像がRetina解像度のスクリーンショットなど過大サイズでないか確認する（`ls -la` や `du -sh` で総容量を把握）
  - 過大な場合は `sips -Z <max_edge_px> "$f" --out "$f"` 等で長辺リサイズし、劇的な削減（数十MB→数MB台）を狙う
  - 同一SVGアイコンが複数箇所にインライン重複していないか確認する。重複があれば `<svg style="display:none"><defs><symbol id="...">...</symbol></defs></svg>` にまとめ、各使用箇所は `<use href="#icon-id">` に置き換える
- **画像の表示順（ファイル名昇順）**
  - ギャラリー等に並ぶ画像・カードが、ファイル名の連番（`#00 → #01 → #02 …`）通りにHTML/データ上で並んでいるか確認する
  - 確認方法: 画像ディレクトリを `ls` してファイル名の実際の昇順を取得し、HTML内の出現順（`data-images` の配列順、または `<article class="card">` の並び順）と突き合わせる
  - ズレがあれば、ファイル名昇順に合わせて要素の並び替え、または `data-images` 配列内の順序を修正する
  - 表示順が壊れていると、ユーザーが期待する時系列・ステップ順とズレて誤読を招くため、パフォーマンスではなく品質観点ではあるが軽微な手戻りコストとして本チェックに含める
- **難易度表示順（初級→中級→上級）**
  - 各ファイル名に含まれる難易度表記（例: `beg`=初級, `mid`=中級, `adv`=上級）を抽出し、ファイル名昇順（`#00→#01→#02…`）に並べたときに、難易度が「初級→中級→上級」の順に緩やかに並んでいるかを確認する
  - 確認方法: ファイル名一覧を昇順ソートし、各ファイルの難易度ラベルを順に並べて `beg, beg, mid, adv, ...` のように書き出し、後戻り（`adv` の後に `beg` が来る等）がないか目視で確認する
  - HTML側の `data-level`（`beginner`/`mid`/`advanced` 等）がファイル名から読み取れる難易度と一致しているかも突き合わせる
  - 順序が崩れている場合は、番号順とレベル順のどちらを優先するかユーザーに確認してから並び替える（両立できない場合があるため、自動修正せず必ず確認する）
  - 「番号順を優先しつつ、同一番号帯内はレベル順（初級→中級→上級）で並べる」という折衷方針が選ばれることが多い。この場合、該当カードのHTMLブロックを丸ごと正しい位置へ移動し、`<!-- N: タイトル -->` のような番号コメントも1から連番になるよう振り直す
  - 並び替え後は `preview_eval` 等でカード要素を `dataset.title` / `dataset.level` の配列として取得し、意図した順序になっているか機械的に確認する（目視だけに頼らない）

#### 3. 📖 可読性

- **型定義（TypeScriptコンパイラがない場合はJSDoc）**
  - 関数に `@param` / `@returns` を付与する
  - 状態変数や複雑な型には `@typedef` でユニオン型・構造を明示する（例: `@typedef {'all'|'beginner'|'mid'|'advanced'} FilterLevel`）
- **関数の単一責任**
  - 同じDOM操作（開閉・スクロールロック等）が複数のイベントハンドラに重複していないか確認する
  - 重複があれば `setXxxOpen(open: boolean)` のような1関数に集約し、各ハンドラはその関数を呼ぶだけにする
  - レンダリング（DOM反映）と状態更新（インデックス操作など）を分離する（例: `renderLightboxFrame()` を状態変更ロジックから独立させる）

### 進め方

1. 対象ファイルを `Read` で全文読み込む
2. 上記3観点でチェックリストを機械的に当てはめ、該当箇所を特定する
3. 見つかった問題を表形式（観点／指摘内容／対応）でユーザーに提示する
4. `Edit` で1項目ずつ修正する。壊れやすい大規模書き換え（script全体の差し替えなど）は1回の `Edit` にまとめてよいが、事前に変更内容を明示する
5. 修正完了後、変更点のサマリー表を提示し、デプロイ等の次アクションが必要なら確認してから進める

### 注意事項

- 存在しないセキュリティリスクを過剰に指摘しない（例: サーバーサイド処理がない静的サイトにSQLインジェクション対策は不要）
- 見つかったバグ（例: 存在しないid参照によるフォーカス制御の失敗）は3観点に厳密に当てはまらなくても、気づいた時点で修正して報告する
- 修正はその場で `Edit` を使って適用し、指摘だけで終わらせない
- 「レビューだけ行い、デプロイ（`git push` / GitHub Pages反映等）は指示があるまで行わない」とユーザーが明言した場合、修正をローカルファイルに適用するところまでで止め、コミットやプッシュは提案のみに留める。次に何をすべきか（デプロイしてよいか等）は都度確認する
